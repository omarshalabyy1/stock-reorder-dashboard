# The project explained, from zero

This page explains the whole project in plain words: what it does, what every word means, where every number comes from, and how to talk about it in an interview. You do not need to know SQL or Power BI to read it.

[← Back to the README](../README.md)

## 1. The project in one minute

A chain has 10 stores, and each store sells the same 50 items. One item in one store is a **shelf**, so there are 500 shelves. Today the stores work by habit: every Monday they count every shelf by hand and top it back up to the same level, whatever the item sells. The supplier delivers on Friday.

That habit fails both ways. The best sellers run empty before Friday, and the slow items sit on the shelf for weeks with cash tied up in them. Nobody can answer, on a given morning:

- Which shelves must be reordered today, and how many units?
- Which shelves are about to run empty?
- How much money is sitting in stock that barely sells?

This project answers them. Every day it loads each store's sales and stock into a database, works out what each item sells on a normal day, compares each shelf with a **reorder point**, emails the reorder list at 7am and feeds a Power BI report. Then it replays the rule over five years of history to check whether it would have seen each empty shelf coming.

Think of the fuel light in a car. It comes on while there is still enough fuel to reach the petrol station. The reorder point is the level where the light comes on. The **lead time** is the drive to the station (here, the 4 days the supplier takes). The **safety stock** is the small reserve for a slow day in traffic: the days when the item sells more than usual.

The sales come from a public file. The stock, deliveries, unit costs and lead times are generated by a script that replays the Monday habit (see Data in the README).

## 2. Words you will meet

| Word | What it means here |
|---|---|
| **Store, item** | Numbers, not names: stores 1 to 10, items 1 to 50. |
| **Shelf** | One item in one store, like "store 1, item 15". 10 stores × 50 items = 500 shelves, each with one row per day. |
| **Units sold** | Units sold that day. A shelf can only sell what it holds, so on an empty day it is 0. |
| **On hand** | Units on the shelf at closing time. |
| **Units received** | Units delivered that morning. In this data, deliveries only land on Fridays. |
| **On order** | Units ordered but not delivered yet. |
| **Position** | On hand + on order: what the shelf will have once the order on its way arrives. |
| **Lead time (`lead_days`)** | Days the supplier takes to deliver after an order. 4 days for every item here, from the items file. |
| **Daily demand** | What the item sells on a normal day now: the average of its last 28 days of sales. |
| **Daily swing** | How much one day's sales move around that average. In statistics this is the **standard deviation**. A big swing means a less predictable item. |
| **Safety stock** | Extra units kept for the days that sell more than average, until the delivery lands. |
| **Service level, 1.65** | The 1.65 in the safety stock formula. It makes the safety stock cover 95% of the normal ups and downs in demand. A higher number means more stock and fewer empty shelves. |
| **Reorder point** | The stock level that triggers an order: what the shelf sells during the lead time, plus the safety stock. |
| **Order quantity** | How many units to order: enough to last until the delivery and 7 days after it. |
| **Days of cover** | How many days the shelf lasts at the current pace: on hand ÷ daily demand. The email calls it "Days left". |
| **Status** | One word per shelf per day: **Out of stock**, **Dead** (stock but not one sale in 28 days), **Reorder**, **Overstock** (more than 30 days of cover) or **OK**. The rules check them in that order and stop at the first that fits. |
| **Slow stock** | Stock with status Overstock: more than 30 days of cover. |
| **Stock value** | On hand × the item's unit cost, in USD (US dollars, `client.currency`). Cash tied up on the shelf. |
| **Stock-out** | The first day a shelf closes empty after a day it did not. Two empty days in a row are one stock-out. |
| **Empty shelf day** | Any day a shelf closes empty. One stock-out can last more than one empty shelf day. |
| **Flag** | A shelf on the reorder list that day (its order quantity is above 0). |
| **Warning days** | For one stock-out: how many days before it the earliest flag came, looking back at most 7 days. |
| **Flagged in time** | A stock-out with at least 5 days of warning: the flag is raised at closing, the order goes in the next morning, and the supplier delivers 4 days after that, before the shop opens. |
| **Backtest** | Running the rule over past days to see what it would have said, then checking it against what really happened. |
| **Best sellers** | The 10 items with the most units sold, all stores together. |
| **Database** | A program that stores tables and answers questions about them. This project uses **PostgreSQL** (often "Postgres"), a free and widely used one. |
| **SQL** | Structured Query Language, the language used to ask a database questions and build tables. The files in `sql/` are SQL. |
| **Table, row, column** | Like a spreadsheet sheet: each row is one thing (one shelf on one day), each column one fact about it (its sales, its stock). |
| **Warehouse** | A database built for reporting, not for running the shop. Here, the PostgreSQL database called `stock`. |
| **CSV** | Comma-separated values: a plain text file of a table, one row per line. The three inputs are CSV files. |
| **`COPY`** | The PostgreSQL command that loads a whole CSV file into a table at once. |
| **Primary key** | The column or columns that make each row unique. For `sales` and `stock` it is date + store + item, so the same shelf and day can never be loaded twice. |
| **Foreign key** | A column that must point to an existing row in another table. Every `item` in `sales` and `stock` must exist in the `item` table, or the load stops. |
| **Check** | A rule on a column that the database enforces, like "units sold is 0 or more". A negative number stops the load. |
| **Materialized view** | A saved query whose result is stored like a table. `forecast` and `stock_rule` are materialized views, rebuilt on every run. |
| **Window function** | A SQL calculation over a sliding set of rows, like "the last 28 days of this shelf". The forecast uses one. |
| **Grain** | What one row of a table stands for. Every table here except `item` has the grain "one shelf on one day". |
| **Fact table, dimension table** | The fact table is the big table of events you add up (`StockRule` in Power BI). Dimension tables are small lookup tables you filter by: `Date`, `Store`, `Item`, `Status`. |
| **Star schema** | One fact table in the middle with dimension tables around it, like a star. The standard shape for Power BI. See [data-model.svg](data-model.svg). |
| **Python, pandas** | Python is a programming language. pandas is its library for tables. `pipeline.py` and the notebook use them. |
| **Notebook** | `analysis/analysis.ipynb`, a file that mixes code, its output and notes. It computes the numbers in the README. |
| **Airflow, DAG, task** | Apache Airflow runs jobs on a schedule. A DAG (directed acyclic graph) is one job: steps joined by arrows that never loop back. Each step is a task. The DAG `stock_reorder` has four: load, forecast, rules, alert. |
| **Cron** | A short text that says when a job runs. `0 7 * * *` means every day at 7:00. |
| **Docker, Docker Compose** | Docker runs programs in a ready-made box called a container, so nobody installs PostgreSQL or Airflow by hand. `docker-compose.yml` says which boxes to start. |
| **Ports 5447 and 8097** | The "door numbers" on your laptop: the warehouse listens on 5447, Airflow's web page on 8097. Each portfolio project uses its own numbers so several can run at once. |
| **`.env`** | A file for secrets: the database password and the Gmail app password. It is never committed; `.env.example` shows its shape. |
| **Gmail app password** | A separate password Google gives a program to send mail, so your real password is never used. |
| **`config/client.yaml`** | The settings a client would change: name, currency, file names, the rule settings, the schedule, colours. YAML is a simple text format for settings. |
| **Power BI, Power Query, DAX** | Power BI is Microsoft's tool for interactive reports. Power Query is the part that loads data. DAX (Data Analysis Expressions) is its formula language, used to write **measures** like "Units to Order". |
| **Theme** | A Power BI file that sets the report's colours and fonts. `theme.py` writes it from `client.yaml`. |

### The rules, with an example

One real row: **store 1, item 15, Sunday 16 July 2017**. It is the first line of the email in the README ([email.png](email.png)). Item 15 is the best seller. That evening the shelf closed with 326 units on hand and nothing on order. The supplier takes 4 days, and one unit costs 29.54.

1. **Daily demand.** The last 28 days are 19 June to 16 July. The shelf sold 2,894 units in them. 2,894 / 28 = 103.357, shown as 103.36.
2. **Daily swing.** The standard deviation of those 28 days' sales is 29.23 units. Some days sold 22, others 154.
3. **Safety stock.** 1.65 × 29.23 × √4 = 1.65 × 29.23 × 2 = 96.46 units.
4. **Reorder point.** 103.357 × 4 + 96.46 = 413.43 + 96.46 = 509.89 units. The email rounds it to 510.
5. **Position and status.** Position = 326 on hand + 0 on order = 326. 326 is at or under 509.89, so the status is **Reorder**.
6. **Order quantity.** Enough for the 4 days to the delivery and 7 days after it: 103.357 × 11 + 96.46 − 326 = 1,136.93 + 96.46 − 326 = 907.39, rounded **up** to **908** units. The email shows 908.
7. **Days of cover.** 326 / 103.357 = 3.15, shown as 3.2. The email calls it "Days left".
8. **Stock value.** 326 × 29.54 = 9,630.04.

The rules use the exact numbers; only the shown values are rounded.

### What happened next, and the backtest

In the history nobody acts on the rule. The stock follows the stores' Monday habit, so the backtest can ask a fair question: had someone ordered on the morning after the first flag, would the delivery have landed before the shelf ran empty?

| Day | On hand at closing | On order | Status |
|---|---|---|---|
| Thu 13 Jul | 0 | 714 | Out of stock |
| Fri 14 Jul | 600 (714 delivered, 114 sold) | 0 | OK |
| Sat 15 Jul | 469 | 0 | Reorder |
| Sun 16 Jul | 326 | 0 | Reorder |
| Mon 17 Jul | 228 | 750 | OK |
| Tue 18 Jul | 100 | 750 | OK |
| Wed 19 Jul | 0 | 750 | Out of stock |
| Thu 20 Jul | 0 | 750 | Out of stock |
| Fri 21 Jul | 627 (750 delivered, 123 sold) | 0 | OK |

- **Monday's 750 is the habit, not the rule.** The store tops the shelf up to the same level, 1,076 units, so it orders 1,076 − 326 = 750. The rule asked for 908.
- **Status goes back to OK on Monday** while the shelf keeps falling, because position now counts the 750 on its way: 228 + 750 = 978 is above the reorder point.
- **The stock-out of Wednesday 19 July was flagged too late.** The first flag in the 7 days before was Saturday 15 July: 4 days of warning. Order on Sunday morning, delivery 4 days later on Thursday 20 July, one day after the shelf ran empty. Wednesday and Thursday are 2 empty shelf days but 1 stock-out.
- **The stock-out the week before was flagged in time.** The shelf ran empty on Thursday 13 July. The first flag was Saturday 8 July: 5 days of warning. Order on Sunday 9 July, delivery on the morning of Thursday 13 July, before that day's sales.

Things that can look wrong but are not:

- **The rule flagged all 4,052 stock-outs, yet only 41% were in time.** A flag came before every one, but most came 3 or 4 days ahead, one day short of the 5 needed.
- **4,434 empty shelf days but 4,052 stock-outs.** A shelf that is empty two days running (like Wednesday 19 and Thursday 20 July above) is 2 empty shelf days and 1 stock-out. 4,434 − 4,052 = 382 extra days.
- **37% in the header, 36.9% on the Power BI card.** The same number, shown with 0 and 1 decimals.
- **OK 4,864,461 + Overstock 2,842,562 = 7,707,023, one more than 7,707,022.** Each value is rounded to the whole dollar on its own. To the cent (from the replay for this guide) they are 4,864,460.64 + 2,842,561.84 = 7,707,022.48.
- **The email shows a reorder point of 510, the rule says 509.89.** The email rounds to whole units for reading; the rule compares the exact value.
- **The row count does not grow or shrink between layers.** `sales`, `stock`, `forecast`, `stock_rule` and Power BI's `StockRule` all hold 913,000 rows, because every table has one row per shelf per day.
- **The status list has Dead, but no shelf is ever Dead.** In this data every shelf sold at least once in every 28 days. The word stays so a real client's dead stock shows up.
- **Daily demand on a shelf's first 27 days uses fewer than 28 days.** The window only holds the days that exist so far; on the very first day there is one day, no swing, and no safety stock.
- **A shelf on Monday says OK while it is about to run empty.** Position counts the Monday order on its way, so the rule sees the shelf as covered. In the history that order is the habit's, not the rule's.

## 5. What the results mean for the business

- **The rule sees every stock-out coming, but often one day too late.** All 4,052 were flagged; 1,643 (41%) early enough to act. The weekly delivery is the reason: 91% of stock-outs start on a Thursday, so a shelf must cross its reorder point by Saturday's closing. One that crosses on Sunday is one day short. Most late flags missed by exactly that day: 2,404 stock-outs had 4 days of warning against the 5 needed.
- **The empty shelves are the best sellers.** The 10 best sellers had 3,919 of the 4,052 stock-outs. Topping every item up to the same level is the root cause: it is too little for them and too much for the rest.
- **Cash sits in slow stock.** On 31 Dec 2017, 2,842,562 of 7,707,022 in stock value (37%) was in shelves with more than 30 days of cover. That is money the stores could free by ordering slow items in smaller amounts.
- **It moves with the seasons.** The slow stock share was 8% at the end of July, when summer sales empty the shelves, and 42% at the end of January. Stock-outs come every summer (see the stock-outs per month chart in the README).
- **The morning list is the daily job.** On a summer Sunday such as 16 July 2017 it says exactly which 111 shelves to reorder and how many units: 98,020 in total.

## 6. Interview questions you can expect

**Explain the project in 30 seconds.**
Stores topped every item up to the same level once a week, so best sellers ran empty and slow items tied up cash. I built a daily pipeline: Python loads sales and stock into PostgreSQL, SQL works out each item's daily demand, safety stock and reorder point, Airflow emails the reorder list at 7am, and Power BI shows what is at risk. Replayed over 913,000 rows, the rule flagged all 4,052 stock-outs, 1,643 of them early enough to order in time, and found 37% of stock value in slow stock.

**How do you know the rule works?**
A backtest. The notebook walks through five years of history and, for every stock-out, finds the earliest flag in the 7 days before. A flag with 5 or more days of warning counts as in time. The same count is written as one SQL query in `powerbi/06-checks.md`, so it can be checked without Python.

**Why did "in time" change from 4 days to 5?**
The first run took 4 days of warning as enough, because the lead time is 4 days, and got 4,047 of 4,052. That ignored the night between the flag at closing and the order the next morning. With 5 days the honest number is 1,643. The README records both, because a correction you hide is worse than a smaller number.

**Why a reorder point with safety stock, and not a fixed shelf level?**
A fixed level ignores what each item sells. The reorder point is set per shelf and per day from its own recent sales, so a best seller gets a high trigger and a slow item a low one. The safety stock grows with how unpredictable the item is, not with a guess.

**Why 28 days and 1.65?**
28 days is exactly four weeks, so each weekday appears four times in the window, and a short window follows the season quickly. 1.65 covers 95% of normal swings. Both are settings in `config/client.yaml`: a client who would rather hold more stock than risk an empty shelf sets 2.05 (98%).

**Why are the rules in SQL and not in Power BI or Python?**
So they are written once. The email, the notebook and every Power BI measure read the status and order quantity from `stock_rule`. Nothing redefines them, so the email and the report can never disagree.

**What happens if the pipeline runs twice?**
Nothing is added twice. `sales` and `stock` have a primary key on date, store and item, and the load inserts with `ON CONFLICT DO NOTHING`, so rows already there are skipped. `forecast` and `stock_rule` are rebuilt from scratch every run.

**Why does the load stop if a day is missing?**
The forecast takes "the last 28 rows" of a shelf as its last 28 days. If a day were missing, 28 rows would cover 29 days and the average would be wrong without any error. So the load counts each shelf's rows against its first and last date and stops if they differ.

**Why does Airflow have its own PostgreSQL?**
In an earlier run, a busy laptop made Airflow kill one of its processes, Postgres restarted every connection, and a shared database stopped the warehouse load halfway (the note is in `docker-compose.yml`). Keeping Airflow's records apart means its trouble never touches the warehouse.

**How would you set it up for a real client?**
Change `config/client.yaml` (name, currency, file names, rule settings, schedule, colours), put their three files in `data/input/` with each item's real lead time in the items file, and run the same commands. No code changes.

## 7. Limits, in plain words

- The stock, deliveries, unit costs and lead times are generated, not taken from a real store. Only the sales come from a public file (see Data in the README).
- In the history nobody acted on the rule. The backtest shows whether an order would have arrived in time, not how the shelves would have looked if the stores had followed the rule every day.
- On an empty day, sales are 0 even though customers wanted more. Those lost sales are not in the data, so the forecast can read a little low right after a stock-out.
- The forecast is a plain 28-day average. It does not know about weekdays, holidays or next month's season.
- The safety stock assumes the lead time is always exactly 4 days. A late supplier is not covered.
- The order quantity ignores pack sizes, minimum orders, shelf space and budget.
- A row already loaded is never updated. If a client sends a corrected count for a past day, the load skips it.
- The Power BI screenshots are not in the README yet.
